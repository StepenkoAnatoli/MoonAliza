# Managed Ollama provider implementation plan

**Goal:** connect managed runtime ownership and the scheduler to bounded native Ollama requests, proving connection identity before sending project content.

**Architecture:** the native helper reports the root PID and creation FILETIME only after Job Object assignment. A second read-only native operation checks an established loopback TCP tuple against that exact process instance. The transport connects and verifies first, then supplies only that connected socket to a private Node HTTP agent, preventing a replacement listener from receiving prompt bytes. A managed runtime owner consumes verified application-supplied runtime/model paths, starts only its own executable, and supplies this transport to the provider under the scheduler lease.

**Spec:** source-plan.md D3–D5; managed-scheduler.md and managed-artifacts.md. Existing full-product authorization covers this stage. Source evidence E-22–E-25 plus E-16/E-19, captured 27 September, passed research preflight with 0 blockers and 8 existing warnings. No new dependency is needed.

- [x] Owned loopback transport: verify before giving the connected socket to HTTP; fixed loopback origin/routes, no credentials/proxy/redirect following, bounded request/response bodies, cancellation and complete cleanup. Tests cover real accepted and unrelated listeners, blocked preflight, redirects and cancelled connections.

Verify model inventory and loaded CPU configuration without inventing GPU identity or qualification. Managed requests disable silent truncation and context shifting.
